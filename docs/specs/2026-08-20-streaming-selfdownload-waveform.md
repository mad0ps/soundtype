# Дизайн: потоковая расшифровка, авто-загрузка модели, визуализация волн

Дата: 2026-08-20
Статус: утверждён к реализации (v1 = пункты 1–4, v2 = пункт 5)
Версия приложения на момент спеки: 0.5.0

## Зачем

Три цели, все проверены на реальных данных и первоисточниках:

1. **Моментальный результат на стопе** — как в Spokenly. Сейчас расшифровка
   стартует ТОЛЬКО после нажатия «стоп» и на длинной записи заставляет ждать
   15–21 с. Нужно, чтобы текст был почти сразу, независимо от длины.
2. **Самодостаточная установка** — сейчас модель и библиотеки (~1.3–1.5 ГБ)
   ставятся вручную через `scripts/fetch-deps.py`. Приложение должно уметь
   скачать их само.
3. **Приятная визуализация записи** — «голосовые волны», как в Spokenly.

## Что уже установлено экспериментами (не перепроверять)

- **Parakeet TDT 0.6b — offline-only.** Настоящего streaming-режима нет ни в
  NVIDIA (для стриминга у них отдельные cache-aware модели), ни в sherpa-onnx
  (`только non-streaming mode поддерживается этим ONNX`). Единственный путь к
  «потоковому» ощущению — **simulated streaming через VAD**.
- **«Instant on stop» = декодирование во время записи.** Spokenly/FluidAudio
  (открыт: github.com/FluidInference/FluidAudio, Swift, там же Rust-порт)
  декодирует речь по VAD-сегментам в фоне, пока пользователь говорит; на стопе
  доделывает только последнюю фразу. Их «streaming»-режим вдобавок использует
  ОТДЕЛЬНУЮ streaming-модель `parakeet-realtime-eou-120m` и Apple Neural Engine
  (RTFx 120–190x) — нам недоступно. Мы копируем **архитектурную идею**, не код.
- **Скорость на нашем железе достаточна.** Замер на OnePlus N10 (int8, CPU,
  num_threads=4): 84 с аудио → 14.8 с декода с VAD (~5.7x), 21.1 с без VAD
  (~4x). Декод успевает за записью → simulated streaming реально даст instant
  на стопе и на этом телефоне.
- **VAD не убирать.** Ранее рассматривали убрать Silero ради качества (без
  него на стыках чуть точнее: «предложение»→«приложение»). Но VAD — это и есть
  механизм нарезки для потокового декода. Оставляем. Небольшой проигрыш
  качества на границах компенсируется тем, что режем на ПАУЗАХ (не рвём слова).
- **Готовый рецепт есть**: `sherpa-onnx/cxx-api-examples/parakeet-tdt-simulate-
  streaming-microphone-cxx-api.cc` — VAD на 512-окнах, декод сегмента на паузе.
  Портируется на Python напрямую.
- **Ловушка (sherpa-onnx issue #2918):** НЕ пере-декодировать растущий буфер —
  он замедляется по мере роста. Декодировать только текущий сегмент.

## Текущая архитектура (кратко)

- `qml/Main.qml` — UI, общается с Python через pyotherside (`setHandler`).
- `py/backend.py` — запись (libpulse ctypes), VAD (silero), Parakeet (sherpa-onnx).
  - `_record()` пишет весь звук в память до стопа.
  - `_transcribe(raw)` ПОСЛЕ стопа: `_split` (VAD режет на сегменты) → `_decode`
    каждый → склейка. Вот тут и теряется время.
- Данные: `~/.local/share/soundtype.n0madd3v0ps/` (`models/`, `runtime/pylibs/`).
- `soundtype.apparmor`: policy_groups = microphone, audio, keep-display-on.
  **Сети нет.**
- Уровень громкости УЖЕ считается: `emit('level', rms/12000)` во время записи,
  в QML используется только чтобы «раздувать» кнопку записи.

## Решения

### 1. Simulated streaming — декод во время записи (v1, ядро)

**Идея.** Перенести декодирование из «после стопа» в «по ходу записи».

**Как.** Поток записи (`_record`) уже читает микрофон чанками. Добавляем в этот
цикл прогон VAD в реальном времени (по 512 сэмплов). Как только VAD сигналит
конец фразы (пауза ≥ `min_silence_duration`) — готовый сегмент кладётся в
очередь; **отдельный worker-поток** берёт сегмент и декодирует Parakeet-ом,
результат сразу эмитится в UI (частичный текст накапливается). На «стоп»
дописываем последнюю открытую фразу через `vad.flush()` → декод → финал.

**Границы модулей.**
- `Recorder` (поток чтения микрофона) — только пишет чанки и гоняет VAD,
  складывает готовые сегменты в `queue.Queue`.
- `Decoder` (worker-поток) — берёт сегменты из очереди, декодирует, эмитит
  `partial`/`segment` события. Не знает про микрофон.
- Общение — через потокобезопасную очередь. Каждый модуль тестируем отдельно.

**Важно.**
- Декодировать ТОЛЬКО текущий сегмент, никогда не весь буфер (issue #2918).
- Параметры VAD как в рецепте sherpa-onnx: threshold 0.5, min_silence 0.25–0.35,
  min_speech 0.20, max_speech (см. п.5).
- События pyotherside: добавить `partial`(idx, text) для живого текста;
  сохранить существующий финальный текст в историю + буфер обмена.

**Поведение по краям.**
- Короткая плотная речь без пауз (8 с одним сегментом): декод один сегмент на
  стопе (~1.9 с) — уже быстро, приемлемо.
- Длинная с паузами: почти всё декодировано по ходу, на стопе — миллисекунды.

### 2. Silero VAD остаётся (v1)

Отмена прежнего «убрать VAD». Он — механизм нарезки для п.1. Качество бережём
резкой на паузах, а не по таймеру.

### 3. Self-download модели (v1)

**UX (вариант B — с подтверждением).** При первом запуске приложение видит,
что `models/parakeet` и `runtime/pylibs` отсутствуют → показывает экран:
«Нужно скачать модель Parakeet (~500 МБ). Желательно по Wi-Fi. [Скачать]».
Качает только после нажатия, с прогресс-баром. По готовности — обычный экран.

**Как.** Логика уже написана в `scripts/fetch-deps.py` (Parakeet + Silero +
python-колёса numpy/sherpa-onnx в те же пути). Выносим её в модуль, вызываемый
из backend по запросу из UI, с эмитом прогресса (`download-progress` события).

**apparmor.** Добавить `networking` в policy_groups. Приложение остаётся
офлайновым по сути (сеть только для первичной загрузки модели) — отразить это
в описании/README, чтобы «сеть у диктофона» не пугала.

**Края.** Нет сети / обрыв / мало места → внятная ошибка + возможность повторить
(докачка `--force`/резюме — по возможности, минимум: чистый повтор).

### 4. Waveform-визуализация «голосовые волны» (v1, плюшка)

**Идея.** Лента вертикальных баров, высота = громкость, прокрутка справа
налево. Как на скрине Spokenly.

**Как (чистый QML).** Массив последних N (~40) значений `level`; на каждый
`level`-event сдвиг + добавление; `Row`/`Repeater` из N `Rectangle`, высота
`bar = base + level*max`. Python не трогаем — данные уже эмитятся.

**Деталь.** Сейчас `level` шлётся ~4 раза/с (раз в аудио-чанк) — для плавной
волны редковато. Варианты: (а) слать `level` чаще (меньший чанк для уровня в
`_record`), (б) сглаживать интерполяцией в QML. Выбор — на этапе плана.

### 5. Overlap + LCS для форс-нарезки (v2, качество)

Только для очень длинной речи БЕЗ пауз, где VAD режет по `max_speech`. Приём
NVIDIA (Canary/Parakeet-v3): куски с ~1 с перекрытием + склейка по token-level
LCS, чтобы не терять слова на форс-границе. TDT stateless между вызовами, так
что контекст только на уровне текста. Выносим в v2 — в обычной диктовке паузы
есть, форс-нарезка редка.

## Изменяемые файлы (ориентир)

- `py/backend.py` — вынести декод в worker-поток, VAD в поток записи, очередь,
  новые события (`partial`, `download-progress`), вызов загрузчика.
- `py/downloader.py` (новый) или рефактор `scripts/fetch-deps.py` в
  импортируемый модуль.
- `qml/Main.qml` — экран первичной загрузки (кнопка + прогресс), waveform-лента,
  обработчик `partial` для живого текста.
- `soundtype.apparmor` — добавить `networking`.
- `docs/ARCHITECTURE.md`, `docs/DECISIONS.md`, `CHANGELOG.md` — обновить.

## Критерии готовности (pass/fail)

1. Длинная запись (~84 с с паузами): текст появляется по ходу; после «стоп»
   финал ≤ ~2 с. (сейчас 15–21 с)
2. Короткая запись (~8 с): результат ≤ ~2 с, качество не хуже текущего.
3. Свежая установка без моделей: экран загрузки → [Скачать] → прогресс →
   рабочее приложение, без ручного запуска скриптов.
4. Нет сети при загрузке → внятная ошибка, приложение не падает, повтор работает.
5. Waveform реагирует на голос во время записи, не тормозит UI.
6. `max_speech`-форс-нарезка не роняет процесс (v1: допустима потеря слова на
   стыке; v2 закрывает overlap+LCS).

## Риски

- **RTFx на телефоне ниже, чем на Apple** — но замер (~4–6x) показывает
  достаточность. Если на других записях просядет < ~2–3x, финальный флеш на
  стопе станет заметным — тогда рассмотреть меньшую модель/меньше потоков.
- **Потоки в Python (GIL)** — декод в C++ (sherpa-onnx) отпускает GIL, так что
  worker реально параллелен записи. Проверить на практике.
- **networking в apparmor** может смущать пользователя у «офлайн» приложения —
  снять вопрос описанием.
- **Собирается/тестируется на телефоне** — сборка через их `scripts/build.sh`;
  проверять на устройстве.
